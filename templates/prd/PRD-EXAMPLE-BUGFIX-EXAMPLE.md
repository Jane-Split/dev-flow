## 三、期望行为 vs 实际行为 【必填】

| 项目 | 内容 |
|------|------|
| **期望行为** | 点击"审批通过"后，系统将 non_conforming_product 表中 id=156 的记录 status 从 1（审批中）更新为 2（已通过），同时填充 approverId=2001（李四）和 approveTime=当前时间。前端列表和详情页状态显示为"已通过"。后续质检员可正常进行处置登记。 |
| **实际行为** | 接口 POST /api/quality/non-conforming-products/156/approve 返回 HTTP 200 `{code: 0, message: "审批通过"}`，但数据库中 status 仍为 1，approverId 和 approveTime 均为 null。前端显示未更新。质检员无法进行处置登记，系统返回"仅已通过的记录可以处置"。 |
| **偏差描述** | 接口层返回成功（HTTP 200），但数据库层未实际更新记录。前端根据接口返回显示成功提示，但刷新后从数据库查到的仍是旧状态，导致显示回退。 |

### 偏差影响分析

| 维度 | 影响 |
|------|------|
| **业务影响** | 所有质量主管的审批通过操作均无效，处置流程完全阻断。7 月 16 日以来共 12 条记录受影响。 |
| **数据影响** | approverId 和 approveTime 缺失，无法追溯审批责任人。数据库记录 status 与审批流实例状态不一致。 |
| **用户影响** | 质量主管以为审批成功，实际未生效。质检员等待处置但无法操作，多次反馈"功能坏了"。投诉量：当天 8 次。 |

## 四、根因分析 【条件必填】

### 4.1 疑似根因

| 项目 | 内容 |
|------|------|
| **根因描述** | `NonConformingProductServiceImpl.approve()` 方法中 SQL 的 WHERE 子句缺少 `id` 匹配条件。执行的 SQL 为 `UPDATE non_conforming_product SET status=2, approver_id=?, approve_time=? WHERE status=1 AND version=?`，未限定记录 ID，导致更新的是所有 status=1 且 version 匹配的记录（若恰好有多条 version 相同的记录）或 0 条（version 不匹配时）。同时方法未检查 `affected rows`，即使 0 行更新也返回成功。 |
| **疑似代码位置** | `com.xxx.quality.service.impl.NonConformingProductServiceImpl` 的 `approve(Long id, String comment)` 方法 |
| **证据** | 1) 日志显示 SQL 执行 `UPDATE ... WHERE status=1 AND version=1`，无 id 条件；2) 数据库中 id=156 的记录 version=1 但恰好在同一时刻有另一条 id=203 且 status=1 version=1 的记录被错误更新；3) 与 id=156 同 version 的记录 id=203 也被错误更新为 status=2 |

### 4.2 相关代码文件

| 文件路径 | 说明 | 需要修改 |
|---------|------|---------|
| `service/impl/NonConformingProductServiceImpl.java` | 审批业务逻辑，approve() 方法 SQL 缺少 id 条件 + 未检查 affected rows | 是（修复 SQL + 新增行数检查） |
| `service/impl/NonConformingProductServiceImpl.java` | reject() 方法，可能存在相同问题，需排查 | 待排查 |
| `mapper/NonConformingProductMapper.java` | XML 中 approve 的 SQL 定义 | 是（修复 WHERE 条件） |

## 五、涉及的业务规则 【条件必填】

### 正确规则

| # | 正确规则 | 触发场景 | 条件（IF） | 行为（THEN） | 否则行为（ELSE） |
|---|---------|---------|-----------|-------------|----------------|
| 1 | 审批通过状态更新 | 审批通过 | 记录 ID 存在 + status=1 + 当前用户有 quality_manager 角色 | UPDATE status=2 + 填充 approverId 和 approveTime | 返回 STATUS_NOT_ALLOWED 或 FORBIDDEN |
| 2 | 更新行数校验 | 审批通过 UPDATE 执行后 | affected rows == 0 | 抛出 UPDATE_FAILED 异常，返回 500 | affected rows == 1，正常返回 |

### 被修复的错误规则

| # | 错误规则 | 错误描述 | 正确规则 |
|---|---------|---------|---------|
| 1 | SQL WHERE 缺少 ID | WHERE 条件只有 `status=1 AND version=?`，缺少 `id=?` | WHERE 必须包含 `id=? AND status=1 AND version=?` |
| 2 | 未检查更新行数 | UPDATE 执行后直接返回成功，未判断 affected rows | 必须检查 affected rows == 1，否则抛异常 |

## 六、涉及的异常场景 【条件必填】

| # | 异常场景 | 正确期望行为 | 当前错误行为 | HTTP 状态码 | 错误码 |
|---|---------|-------------|-------------|-----------|--------|
| 1 | 更新 0 行（无匹配记录） | 返回 500 + UPDATE_FAILED "数据已被修改，请刷新后重试" | 返回 200（静默失败） | 500 | UPDATE_FAILED |
| 2 | 更新多行（意外匹配） | 应不会发生（有唯一 ID 匹配），但若发生应记录 ERROR 日志 | 静默更新多条记录 | - | - |

## 七、修复范围限定 【必填】

### 7.1 允许变更清单

| # | 修复项 | 涉及文件/类/方法 | 修改类型 | 修改说明 |
|---|--------|---------------|---------|---------|
| 1 | 修复 approve SQL | `NonConformingProductMapper.xml` 中 `approve` SQL | 修改 | WHERE 子句增加 `AND id = #{id}` |
| 2 | 新增 affected rows 检查 | `NonConformingProductServiceImpl.approve()` | 修改 | UPDATE 后检查 `affected rows`，为 0 时抛 `BusinessException(UPDATE_FAILED)` |
| 3 | 排查并修复 reject 方法 | `NonConformingProductServiceImpl.reject()` + 对应 Mapper XML | 修改（若存在同类问题） | 排查 reject SQL 是否也缺少 id 条件，若有则同步修复 |
| 4 | 补充单元测试 | `NonConformingProductServiceImplTest` | 新增 | 覆盖：正常审批、id 不存在（0 行更新）、并发审批（乐观锁冲突）、reject 同类场景 |
| 5 | 修复已受影响数据 | 数据库脚本 | 新增 | 将 7/16 以来被错误更新的记录（id=203 等）恢复为正确状态（需人工确认） |

### 7.2 禁止变更声明 【必填】

| 项目 | 说明 |
|------|------|
| **不允许修改的文件/类** | Controller 层代码、前端代码、DTO/VO 类、配置文件、其他 Service 类（如 DispositionService）、列表查询逻辑 |
| **不允许变更的业务逻辑** | 创建不合格品、提交审批、处置登记等其他功能不变更。审批驳回逻辑仅在排查发现同类问题时一并修复，否则不改动。 |
| **不允许的数据库变更** | 不新增表、不修改表结构、不新增字段、不加索引、不修改已有数据（除 §7.1 第 5 项明确的数据修复外） |
