# PRD 模板 — Bug 修复

> 适用范围：**Bug 修复**（逻辑错误、数据错误、显示错误、并发问题、兼容性问题等）
>
> 填写规则：`【必填】` 必须填写 · `【条件必填】` 触发条件满足时填写 · `【建议】` 选填可提升质量
> 不删除任何章节标题，无内容时填"无"。

---

## 一、Bug 基本信息

### 1.1 概述 【必填】

| 项目 | 内容 |
|------|------|
| **Bug 标题** | 一句话描述现象，不超过 30 字（如"审批通过后状态未更新为已通过"） |
| **Bug 类型** | 逻辑错误 / 数据错误 / 显示错误 / 并发问题 / 兼容性问题 / 其他 |
| **严重程度** | P0(阻断) / P1(严重) / P2(一般) / P3(轻微) |
| **Bug 来源** | 线上反馈 / 测试报告 / 内部发现 |
| **发现时间** | YYYY-MM-DD HH:mm |
| **发现人** | 姓名/角色 |
| **影响范围** | 影响的用户群体和业务场景 |
| **优先级** | P0(紧急) / P1(高) / P2(中) / P3(低) |

### 1.2 环境信息 【建议】

| 项目 | 内容 |
|------|------|
| **发生环境** | 线上 / 测试 / 预发布 |
| **浏览器/客户端** | 如：Chrome 120 / Android App v2.3.1 |
| **涉及服务** | 如：quality-management v1.5.2 |
| **是否必现** | 必现 / 间歇性（频率） |
| **特定条件** | 仅在特定条件下出现 |

## 二、Bug 复现步骤 【必填】

> 步骤必须足够详细，每步写明具体操作、输入数据和期望结果。
> 首次出现异常的步骤标注 ❌。

### 2.1 前置数据准备 【条件必填】

> 需要特定数据才能复现时填写。

| # | 准备项 | 数据说明 | 数据状态要求 |
|---|--------|---------|-------------|
| 1 | 不合格品记录 | productId=1001, batchNo="BATCH-001" | status=1（审批中） |

### 2.2 操作步骤 【必填】

| 步骤 | 操作描述 | 输入数据 | 期望结果 | 实际结果 |
|------|---------|---------|---------|---------|
| 1 | 登录系统，进入不合格品管理页 | 用户：质检员张三 | 页面正常加载 | 页面正常加载 |
| 2 | 以质量主管登录，审批通过 | userId=2001, 意见="同意" | 状态变为"已通过" | **状态仍为"审批中" ❌** |

---

## 三、期望行为 vs 实际行为 【必填】

| 项目 | 内容 |
|------|------|
| **期望行为** | 审批通过后，状态应从"审批中(1)"更新为"已通过(2)"，同时记录审批人ID和审批时间 |
| **实际行为** | 接口返回 HTTP 200，但数据库中 status 仍为 1，approveUserId 和 approveTime 未填充 |
| **偏差描述** | 前端调用成功，后端数据库未正确更新 |

### 偏差影响分析

| 维度 | 影响 |
|------|------|
| **业务影响** | 已审批通过的记录无法进行后续处置操作，流程中断 |
| **数据影响** | 审批人和审批时间缺失，无法追溯 |
| **用户影响** | 审批人以为成功，实际记录卡在审批中 |

---

## 四、根因分析 【条件必填】

> 已知根因可缩短定位时间；不知道根因可跳过，系统会自动分析代码。

### 4.1 疑似根因

| 项目 | 内容 |
|------|------|
| **根因描述** | approve() 方法 SQL 的 WHERE 子句缺少 ID 匹配条件，乐观锁导致 UPDATE 匹配 0 行，但方法未检测更新行数 |
| **疑似代码位置** | `NonConformingProductServiceImpl.java` 的 `approve()` 方法 |
| **证据** | 日志显示 SQL 执行 `UPDATE ... WHERE status=1 AND version=1`，未限定记录 ID |

### 4.2 相关代码文件

| 文件路径 | 说明 | 需要修改 |
|---------|------|---------|
| `service/impl/NonConformingProductServiceImpl.java` | 审批业务逻辑 | 是（修复 SQL + 检查行数） |

## 五、涉及的业务规则 【条件必填】

> 仅当 Bug 由业务规则错误导致时填写。

| # | 正确规则 | 触发场景 | 条件（IF） | 行为（THEN） | 否则行为（ELSE） |
|---|---------|---------|-----------|-------------|----------------|
| 1 | 审批通过状态更新 | 审批通过 | ID 存在 + status=1 + 有权限 | status→2 + 记录审批人/时间 | 返回 STATUS_NOT_ALLOWED |

### 被修复的错误规则

| # | 错误规则 | 错误描述 | 正确规则 |
|---|---------|---------|---------|
| 1 | SQL 缺少 ID 条件 | WHERE 子句只有 status 和 version | 必须包含 id 条件 |

## 六、涉及的异常场景 【条件必填】

> 仅当 Bug 由异常处理缺失或错误导致时填写。

| # | 异常场景 | 正确期望行为 | 当前错误行为 | HTTP 状态码 | 错误码 |
|---|---------|-------------|-------------|-----------|--------|
| 1 | 更新 0 行 | 返回 500 + UPDATE_FAILED | 返回 200（静默失败） | 500 | UPDATE_FAILED |

---

## 七、修复范围限定 【必填】

> 核心原则：**最小变更**，超出范围的修改会被审计拦截。

### 7.1 允许变更清单

| # | 修复项 | 涉及文件/类/方法 | 修改类型 | 修改说明 |
|---|--------|---------------|---------|---------|
| 1 | 修复 approve SQL 条件 | `ServiceImpl.approve()` | 修改 | WHERE 增加 `id = #{id}` |
| 2 | 新增更新行数检查 | `ServiceImpl.approve()` | 修改 | affected rows 为 0 时抛异常 |
| 3 | 补充单元测试 | `ServiceImplTest` | 新增 | 覆盖修复场景 |

### 7.2 禁止变更声明 【必填】

| 项目 | 说明 |
|------|------|
| **不允许修改的文件/类** | Controller 层代码、前端代码、配置文件、其他 Service 类 |
| **不允许变更的业务逻辑** | 审批流程本身不应改变，仅修复状态更新；其他功能（创建、驳回、处置）不应改动 |
| **不允许的数据库变更** | 不新增表、不修改表结构、不加索引 |

## 八、验收标准 【必填】

> 双维度：**修复验证**（Bug 已修复）+ **回归验证**（未引入新问题）。
> 每条标准必须是可自动化验证的断言。

### 8.1 修复验证 【必填】

| # | 验收场景 | 验收条件（断言） | 优先级 | 测试级别 |
|---|---------|----------------|--------|---------|
| 1 | Bug 修复验证 | 按 §2 复现步骤执行→数据库 status=2 + approveUserId 已填充 | must | e2e |
| 2 | 刷新页面验证 | 刷新页面→状态显示"已通过" | must | e2e |
| 3 | 更新失败异常处理 | 模拟 affected rows=0→HTTP 500 + code=UPDATE_FAILED | must | unit |

### 8.2 回归验证 【必填】

| # | 回归场景 | 验收条件（断言） | 优先级 | 测试级别 |
|---|---------|----------------|--------|---------|
| 1 | 创建功能 | 创建不受影响→HTTP 200 + status=0 + recordCode 格式正确 | must | e2e |
| 2 | 提交审批 | 提交不受影响→status 正确更新为 1 | must | e2e |
| 3 | 审批驳回 | 驳回不受影响→status=3 + rejectReason 已保存 | must | e2e |

### 8.3 边界验证 【建议】

| # | 边界场景 | 验收条件 | 优先级 | 测试级别 |
|---|---------|---------|--------|---------|
| 1 | 不存在的记录审批 | 传入不存在 ID→HTTP 404 + RESOURCE_NOT_FOUND | should | unit |
| 2 | 重复审批 | 已审批通过记录再次审批→HTTP 400 + STATUS_NOT_ALLOWED | should | unit |
